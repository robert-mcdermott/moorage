# Changelog

## 0.6.0 (2026-11-04)

Moorage 0.6.0 is about a server you can rely on. On Linux, apps are kept apart from one another. Backups and restoring are built in, and were tried on real services. People can sign in with a second factor, through your identity provider, or through a proxy. A server can upgrade itself, and go back. Moorage is now open source, under the Apache License 2.0.

To upgrade from 0.5.0, run the installer once and restart the server, as `moor server upgrade` starts with this version. Running apps are taken over without a restart. Some things behave differently:

- **On a server that runs as root on Linux, apps get users of their own as they next start.** That is the system service, as `level = "auto"` under `[isolation]` means this. An app can then only write to `$MOORAGE_DATA_DIR` and `$TMPDIR`, as its build is read-only, and cannot read what only root can. `level = "none"` keeps it as it was while you look into anything that minds. Instances that go on through the upgrade go on as root until they restart: **Settings → System** and the app's page say which, and `moor restart APP` does it with no downtime. See [isolation](docs/isolation.md).
- **To go back to 0.5.0,** stop the server, put the copy of the database that this version kept in `backups` in the data directory in the place of `moorage.db`, and give the installer `MOOR_VERSION=v0.5.0`. 0.5.0 refuses a database that has moved on.
- **A site's directory has to be inside its build.** One reached through a link to somewhere else now fails the build.

### Added

- **Apps kept apart on Linux.** A server running as root gives each app an operating system user of its own, and its builds another: its data is its own, its build is read-only, and other apps cannot read its secrets. `level = "sandbox"` under `[isolation]` in `server.toml` adds Landlock and `no_new_privs`. See [how apps are kept apart](docs/isolation.md).
- **`[resources]` outside containers.** Memory, CPU and process limits for any app, enforced by the kernel where the server runs as root on Linux. Elsewhere an instance that stays over its memory limit is restarted, and the console says what is not held to. An instance killed for its memory says that it ran out of memory.
- **Backups.** `moor server backup` and **Settings → Backups** make a backup of a running server, on demand or on a schedule, to a directory or a bucket on S3 or a service like it. `moor server restore` brings it all back: apps, data, secrets and accounts. A restore checks everything before it changes anything, and is tried in CI. See [backups](docs/backups.md).
- **Two-factor sign-in.** **Your account → Two-factor** adds a code from an authenticator app to signing in, with recovery codes for if you lose it. See [accounts](docs/accounts.md#two-factor-sign-in).
- **Single sign-on.** **Settings → Sign-in** connects to any OpenID Connect provider, with accounts made the first time, roles from groups, and an option to turn off passwords. `trusted_header` under `[auth]` believes a proxy that signs people in. See [how people sign in](docs/sign-in.md).
- **`moor server upgrade`.** A server upgrades itself: it checks a release against its published checksum, keeps a copy of the database and the binary, swaps them, restarts, and goes back by itself if the new version does not come up. `--rollback` goes back later on. Apps keep running throughout. Releases now come with a list of what went into them, and an attestation of the workflow that built them. See [upgrading](docs/install.md#upgrading).
- **The server's configuration, as a file.** `moor server config export` writes out people, projects, registries, notifications, backups and sign-in, with no secrets, and `moor server config import` brings it in on that server or another, with `--dry-run` to look first. See [the server's configuration](docs/backups.md#the-servers-configuration).
- **Node.js downloads are checked against its signature.** The checksums of a Node.js release have to be signed by one of its releasers, whose keys come with moor. A new releaser's key needs a new moor, or `signatures = "warn"` under `[toolchains]`. A signature that is wrong is always refused.

### Fixed

- **A deployment could bring the release before it back.** What keeps instances running could look at the current release just before a deployment recorded the new one, and start an instance of the old one after the rollout had finished. That instance then took the traffic, until the next deployment. It was rare, and has been possible since 0.1.0. A release is now recorded before its instances take the traffic, and an instance of any other release is stopped.

## 0.5.0 (2026-11-04)

Moorage 0.5.0 is about apps once they are running. They can have cron jobs and one-off commands, charts of how they are doing, and notifications when they are not. Drop a folder in the console and it is a static site, with every release at an address of its own. A server of 4 CPUs and 8 GB holds 60 environments with sleep on, as [measured](docs/install.md#how-big-a-machine). Moorage is now licensed under the [Apache License 2.0](LICENSE).

Upgrading from 0.4.0 needs no steps of its own: replace `moor` and restart the server, and running apps are taken over without a restart. Some things behave differently:

- **`[[cron]]` in a manifest now runs.** It was accepted and did nothing, and `moor manifest validate` warned of that. Its jobs start with the next deployment.
- **`[vars.NAME]` now counts.** A deployment fails early if a `required` one is missing, and one to `generate` is made.
- **`watch` in `[app]` now counts.** A push that touches none of those paths is kept, and not deployed.
- **People are told when things fail.** In the console, maintainers of a project, its administrators and whoever pushed a deployment see notifications, with no setup. Nothing leaves the server until you add a channel and a rule.
- **Metrics take room.** About 6 MB for a busy environment, kept for a year.
- **`moor deploy --static` now follows the manifest's `[environments.*]` and `[previews]`,** and `keep_releases`. It ignored them, so that a site you meant to gate with `access` in its manifest may have been open, and is now closed as it says.
- **Commands run with their environment's variables.** A release command ran with `[env]` alone, and now has `[environments.NAME.env]` over it, as the app itself always did.

### Fixed

- **With Moorage's own CA, the addresses of environments and previews had no certificate,** so that a browser got a TLS error. They have one now.
- **A long request through a login gate with a token ended only with the gate, and not with the token.** Revoking the token ends it now, within a minute.
- **Following an app's logs or a run's output now ends when you may no longer see them,** within a minute.
- **A server started right after another stopped could say that the other was still using its data directory,** if a process it was starting at that moment held a copy of the lock. Stopping now lets go of the lock whatever else holds a copy.

### Added

- **Drop a folder in the console (wave 5, slice 4).** On an app's **Deploy** page, drop a folder or choose one, and it is a live static site a moment later. `.git` and `.env` files stay out of it. See [static sites](docs/static.md).
- **Every release of a static site at its own address.** `docs--production--v12.apps.example.com` serves that release as long as it is kept, behind the same gate as its environment, to compare versions or show someone an exact build. `moor releases` lists them.
- **Notifications (wave 5, slice 3).** Moorage says when a deployment fails, an app keeps crashing, a cron job fails or the server's disk is nearly full: in the console for those it concerns, with no setup, and through signed webhooks, Slack, Microsoft Teams, Discord and email for whatever rules you add, of the whole server, a project or an app. One crash-looping app sends one message and not hundreds, then a word when it recovers. `moor notifications`, and see [Notifications](docs/notifications.md).
- **Metrics (wave 5, slice 2).** Requests, response times, CPU and memory for every environment, kept for a year with nothing else to run. An app's **Metrics** tab has them as charts from the last 15 minutes to the last 30 days, with each release marked, its page has the last hour at a glance, and the list of apps has each one's requests. `moor metrics`, and `/metrics` for Prometheus.
- **Cron jobs (wave 5, slice 1).** `[[cron]]` in the manifest: five-field schedules or `@daily` and `@every 15m`, time zones, time limits, what to do about overlaps, and which environments. `moor cron`, and a **Cron** tab with when each next runs and how it last went. The last 100 runs of each are kept, with what they said.
- **`moor run -- COMMAND`.** Runs a command in the current release, with its variables and data, shows what it says, and ends with its exit status. The console has a box for it.
- **`moor restart PROCESS`.** Replaces the instances of one process, and leaves the others running.
- **What an app expects.** `[vars.NAME]`: a deployment fails early if a `required` one is missing, and one to `generate` is made once for each environment.
- **`watch` in `[app]`.** A push that touches none of those paths is kept, not deployed.

## 0.4.0 (2026-11-03)

Moorage 0.4.0 gives every branch a place of its own, and says who can reach it. Push a branch and it gets its own build, address and data, which sleeps when nobody is using it and goes when its branch does. Staging, promoting what it runs to production, and locks come with it. Each environment can be open, behind a password, for those signed in, or only for people with a share link. Apps can have domains of their own, and belong to projects, in which people have roles, with an audit log of who did what.

Upgrading from 0.3.0 needs no steps of its own: replace `moor` and restart the server, and running apps are taken over without a restart. Three things behave differently:

- **Pushing a branch other than the default now deploys it,** as a preview. `enabled = false` in `[previews]` keeps branches as they were.
- **Previews are for those signed in with a role in the app's project.** To share them with people who have no account, make a [share link](docs/access.md#share-links), or set `preview = "public"` under `[access]` in `server.toml`.
- **New servers set up as you keep everything in `~/.moorage`** on macOS and Linux. A server that already exists is found where it is.

### Added

- **Access gates (wave 4, slice 6).** Each environment can be open to anyone, behind a shared password, for those signed in to Moorage, whom the app hears named in `X-Moorage-User` and its fellows, or only for people with a share link, with a list of addresses on top of any of them. `moor access`, `moor share`, an **Access** tab in the console, `access` in the manifest and `[access]` in `server.toml`. Previews are for those signed in with a role, unless you say otherwise: if you share previews with people who have no account, set `preview = "public"` under `[access]` in `server.toml`, or make a share link.
- **Your own domains, and paths (wave 4, slice 7).** `moor domains add portal.example.com`, which serves once its DNS points here, or `tools.example.com/reports`, so that several apps share a hostname. And `routing = "path"`, for servers with no wildcard DNS: apps at `/<app>/`, with a console on its own hostname.
- **`X-Moorage-Proxy-Token`,** which an app that does not trust what else runs on its machine can check against `$MOORAGE_PROXY_TOKEN`, to know that a request came through Moorage.
- **Sleep and wake (wave 4, slice 5).** An environment left idle stops its instances, and the next request starts them and waits: a browser gets a page that says it is waking up, and reloads itself. Previews do it after 30 minutes unless told otherwise, and others with `sleep_after` in `[environments.NAME]`. `sleep = false` keeps a process running, `moor sleep` and `moor wake` do it by hand, and it stays asleep across a restart of the server.
- **Previews (wave 4, slice 4).** Push a branch, and it gets its own build at its own address, `shop--my-branch.apps.example.com`, with production's variables (except those set `--production-only`), its own empty data directory and `noindex`. Deleting the branch destroys it, and so does going unused for seven days, unless it is pinned. **Previews** in the console and `moor previews` have them all. If you push other branches to a Moorage remote today, note that they will now deploy: `enabled = false` in `[previews]` keeps them as they were.
- **Named environments.** `[environments.staging]` with a branch, `moor environments create`, or `moor deploy --env staging`: a place that stays, with its own address, variables and data. Every page of an app in the console and every command with `--env` works on them.
- **`moor promote --from staging`.** Releases the exact build one environment runs to another, in seconds, and warns if it was built with other build variables.
- **`moor lock` and `moor unlock`.** Stop deployments to an environment, so that the next push does not replace a rollback. A rollback's page offers it.
- **Renaming and deleting apps (wave 4, slice 3).** `moor apps rename`, `moor apps delete`, and an app's Settings page, which also moves it to another project. Renaming moves everything of it and starts it again under the new name. Deleting says how much room each part takes, asks for its name, and can keep its data directory. `moor apps info` and `GET /api/v1/apps/{app}` say how much room an app takes.
- **Projects and roles (wave 4, slice 2).** Apps belong to projects, and people have roles in them: viewers see an app and its logs, deployers also deploy, restart, roll back and scale, and maintainers also change its variables and the project's members. Those with no role cannot tell its apps exist. An upgrade changes nothing: every app goes in a `default` project where everyone is a maintainer, until you say otherwise. `moor projects`, `moor apps create --project`, `moor apps move`, and a Projects page; the console shows what your role allows. See [Projects and roles](docs/accounts.md#projects-and-roles).
- **The audit log.** Every change through the API or the console, every sign-in, push and secret revealed, kept for a year, with who, from where, what to, and how it went. `moor audit`, `GET /api/v1/audit`, and Settings for administrators.
- **Revealing a secret.** `moor env reveal NAME`, and a button for maintainers. It shows the value once, and is recorded.

### Fixed

- **A tab in the address after signing in could send you to another site.** The `next` of the sign-in page now refuses anything a browser would take away before looking.
- **`X-Real-IP` said what a client claimed** behind a proxy, rather than what the proxy saw. It now goes by the nearest address that is not a trusted proxy.
- **Headers such as `X_Moorage_User` reached apps** that read an underscore as a dash. They are now removed.

### Changed

- **`~/.moorage` is the default home (wave 4, slice 1).** Set up as yourself on macOS or Linux, a server keeps `server.toml` and `data/` in `~/.moorage`, and `moor` its `config.toml`: one folder, the same on both, short to type. An existing server stays where it is, and `moor` finds it. `XDG_CONFIG_HOME` and `XDG_DATA_HOME` still win on Linux, if they are set. Servers set up as root and Windows have not moved.

## 0.3.0 (2026-11-03)

Moorage 0.3.0 has a web console. Everything you run with `moor` you can now see and do at the server's console address: deploy, scale, restart and roll back apps; watch a deployment's stages and log as they happen; follow and search logs; change variables; manage your keys and tokens, and, as an administrator, users and registries. Every page works without scripts, on a phone, and in Chromium, Firefox and WebKit, which CI now drives for real. It also installs in one line, and gains `moor scale`, `moor redeploy` and `moor password`.

Upgrading from 0.2.0 needs no steps of its own: replace `moor` and restart the server, and running apps are taken over without a restart. Two things take a little more or a little less room from now on: an upload's source is kept beside its build for `moor redeploy`, until the build is collected; and the logs of instances that stopped more than 14 days ago are removed.

### Added

- **Logs in the console (wave 3, slice 4).** Every instance's output, live, merged by time: by process or instance, time range, text and source, with an app's builds, requests and events a click away, and only its problems at another. A line that is a JSON object reads as its message and fields, and errors and warnings stand out. Pause, wrap, older lines and download. `moor logs` and the API have the same: `--source`, `--grep`, `--since`, `--until`, `--instance` and `--problems`.
- **Variables in the console.** With where each comes from, and whether something overrides it. Change one and it is released; or save it and release it later, which the page keeps saying. **Edit as text** takes a whole `.env` and says what it would change before it does.
- **Your account in the console.** Your password, SSH keys, API tokens, each with what it can do, for which apps and until when, and your sessions. `moor password`, and `POST /api/v1/me/password`: it ends your other sessions.
- **Settings for administrators.** What `server.toml` says; users, with invitation links, roles and disabling; registries' credentials; and a System page with what `moor server doctor` finds, also at `GET /api/v1/server/doctor`.
- **Apps and deployments in the console (wave 3, slice 3).** The apps list says how each app stands. An app's page has its instances and their health, its deployments and activity, and Deploy, Redeploy, Restart, Roll back and Scale. A deployment's page shows its stages and log as they happen, the resolved manifest and what changed since the release before: of variables, their names only. **New app** says how to deploy one; a source archive or an image can be deployed from the page. See [the console](docs/console.md).
- **`moor scale web=3 worker=1`.** How many instances of each process run: new ones start beside those running, those beyond the number finish their requests and stop, and an instance that cannot start leaves the app as it was. The number stays, over the manifest's `instances`, for the releases to come. In the API: `PATCH /api/v1/apps/{app}/envs/{env}`. Planned for 0.5.0, and here because the console needed it.
- **`moor redeploy`.** Builds again what the current release was built from: the same commit, upload or image name. For this, a build now keeps a copy of its upload, or of an image's manifest, as `source.tar.gz` beside it, until the build is collected; a release built before this version cannot be redeployed, and says so. A release uploaded ready to run has nothing to build.
- **`moor releases show vN` and `moor releases diff vN vM`.** What a release runs, and what changed between two.
- **Every deployment has a log.** A rollback, a change of variables and an upload ready to run wrote none.

- **The web console begins (wave 3, slice 2).** Signing in now leads to the console: the apps, with their addresses and releases; **Activity**, a timeline of what happened; and **Getting started**, which says how the server looks, what to install and how to deploy, and watches for your first deployment. Pages update as things happen, over one stream of events. `⌘K` or `Ctrl+K` jumps to an app, a page or an action. It has light and dark themes that follow the system or your choice, works at phone width, meets WCAG AA contrast, and works without scripts: every page is plain HTML and forms, under a strict Content-Security-Policy with no inline scripts or styles. See [The web console](docs/console.md).
- **Events.** Deployments, releases, changes of variables (their names, never their values), instances that exit, sicken and recover, and the server starting are recorded for 90 days. `moor events` shows them and `-f` follows them; `GET /api/v1/events` lists them and `GET /api/v1/events/stream` follows them as server-sent events, catching up after a reconnection. A token restricted to an app sees only that app's.
- **One line to install (wave 3, slice 1).** `curl … install.sh | sh` on macOS and Linux, and `irm … install.ps1 | iex` in PowerShell on Windows 11. Each picks the file for the computer from the latest release, requires exactly one matching SHA-256 checksum, runs the downloaded program's version check, and only then puts it in place, so a failed download never replaces a working copy. Neither needs administrator rights: `moor` goes to `~/.local/bin`, or to `/usr/local/bin` as root, or on Windows to `%LocalAppData%\Programs\Moorage`, which is added to the user `PATH`. Running one again upgrades `moor` without disturbing a running server or its apps, including on Windows, where the running file is moved aside; `MOOR_VERSION` installs a particular release. See [Installing Moorage](docs/install.md).

### Changed

- **`moor logs` reads more.** With `--source` it adds an app's builds, requests and events to its instances' output. A line that is a JSON object prints as its message and fields; `--json` still has the line as written.
- **A rollback, a change of variables and an upload ready to run now write a log,** like any other deployment.
- **Scaling comes earlier than planned.** The roadmap had it in 0.5.0; the console needed it.

## 0.2.0 (2026-11-03)

Moorage 0.2.0 is for teams. `git push` deploys an app, over SSH or HTTPS, with no `git` or `sshd` needed on the server, and shows the build in your terminal. Accounts, sign-in from any machine and scoped API tokens say who did what. Apps with a `Containerfile`, or an image from a registry, run in containers under Podman or Docker, released and rolled back like any other app. `moor trust` makes browsers accept the certificates of a server's own CA, `moor server doctor` checks a server and says how to fix what it finds, and `moor server proxy-config nginx` writes the configuration for running behind nginx. The documentation has moved up to `docs/`, with complete examples. The web console comes in 0.3.0.

Upgrading from 0.1.0 needs no steps of its own: replace `moor` and restart the server, and running apps are taken over without a restart (see [Upgrading](docs/install.md#upgrading)). Upgrade `moor` on other machines too: the API's lists now come in pages, which an older `moor` cannot read.

### Added

- **Deploys by git push (wave 2, slice 2).** Every app has a git repository on the server, served over SSH (port 2222, `listen.ssh`) and HTTPS (`/git/<app>.git` on the console's hostname) by Moorage itself: no `git` or `sshd` is needed on the server. `moor keys add` registers an SSH key (Ed25519, ECDSA, or RSA of 3072 bits or more); `moor git remote` adds the app's remote to a repository, and `git push moorage main` deploys, with the build streamed back as `remote:` lines. The production branch is the repository's default branch (`main`, or the first branch pushed); other branches and tags are kept, not deployed. A failed deploy fails the push and leaves the branch where it was; `Ctrl-C` leaves the deploy running. The first push creates the app. `[skip deploy]` in a commit's message, or `git push -o skip-deploy`, keeps a commit without deploying it; `-o detach` accepts the push at once; `-o env=production` deploys any branch. Over HTTPS, `moor git remote --http` sets up `moor git credential`, which gives git the API token for the server's own git URL only. Repositories can be cloned back. `moor deployments` shows the branch and commit each push deployed, and other commands find the app from the `moorage` remote. See [Deploying with git push](docs/git.md).
- **Accounts (wave 2, slice 3).** Users with email and password (Argon2id, at least 12 characters, common passwords refused) and a role: admins manage users, and until projects arrive members may do everything with apps. `moor server init` prints a one-time setup link to create the first account, so that nobody can race to claim a new server. `moor login URL` signs in from any machine by approving it in a browser (or `--with-token`), saving a context; `moor logout`, `moor whoami` and `moor context` go with it. `moor server users` creates users, who choose a password with a one-time link, and changes roles, disables and enables them. `moor tokens` makes API tokens with a scope (`read`, `deploy`, `admin`), an optional app and an expiry, stored only as hashes. SSH keys belong to their user. Git follows suit: pushes are recorded as their user's, tokens need the right scope, and a disabled user's keys and tokens stop working. Failed sign-ins and SSH handshakes slow down per address and account, and are logged as security events. Minimal pages on the console's hostname serve the claim, signing in, choosing a password and approving a sign-in; the session cookie is host-only, and forms and cookie-authenticated API requests need a CSRF token. See [Accounts and access](docs/accounts.md).
- **Containers (wave 2, slice 4).** An app with a `Containerfile` or `Dockerfile`, or `runtime = "dockerfile"`, is built into an image by Podman or Docker; `runtime = "image"`, or `moor deploy --image REF`, runs one that is built already, pinned to its digest, so that restarts and rollbacks run exactly that image. Each runs like any other app: zero-downtime releases, health checks, rollbacks, logs, release commands, workers, variables and secrets. Containers publish only on the loopback interface, run with `no-new-privileges` and an init process, and get the environment's data directory at `/data` (`[storage].mount`). `[container]` sets the port, the user and the build, and `[resources]` memory, CPU and process limits. Moorage owns restarts: a container that exits is restarted by the process's `restart` policy, more slowly when it keeps exiting, and a kill for running out of memory is reported where the engine says so. Containers outlive the server, which finds them again by their labels, with no output lost or recorded twice; a server manages only its own. `moor registry login` keeps a private registry's credentials encrypted on the server. `[containers].engine` in `server.toml` chooses the engine: Podman if it is installed, or else Docker. CI runs all of it on both. See [Running apps in containers](docs/containers.md) and the new [Guestbook example](examples/container-go).
- **TLS and operations (wave 2, slice 5).** `moor trust` puts a server's CA into the system's list and, on Linux, the browsers' own, and `--remove` takes it back. From the server's own machine it asks nothing; from elsewhere nothing vouches for the answer, so it shows the CA's fingerprint and what it may sign for, and asks, or takes `--fingerprint`. It refuses a server whose certificate does not come from the CA it offers. `moor server status` and the server's log show the fingerprint. `moor server proxy-config nginx` writes a configuration for nginx, which CI runs for real, deploying and pushing through it. `moor server doctor` checks a server, running or not, and says how to fix what it finds: its listeners, DNS, certificates, the container engine, the data directory and its keys, disk space, the clock, kernel features, and apps that can be reached without the router. `--public-url` checks the whole path through a proxy: forwarded headers, an app's hostname, WebSockets, streaming and large uploads, and with `--timeouts`, long silences. `moor server resolver install` makes `*.localhost` resolve for everything on macOS, with a rule in `/etc/resolver` and a small DNS responder in the server (`listen.dns`) that answers on loopback only. See [TLS and trusting the server](docs/tls.md), [Behind a TLS proxy](docs/proxy.md) and [When something is wrong](docs/troubleshooting.md).
- **The API's contract.** Every route declares the permission it requires, and a test enumerates them. [`docs/openapi.json`](docs/openapi.json), an OpenAPI 3.1 document generated from the routes and types and checked against them, is served at `/api/v1/openapi.json`. Errors can say what is wrong field by field. See [The API](docs/api.md).
- **Examples (wave 2, slice 1).** [`examples/`](examples/README.md) has four complete apps, each ready to deploy with `moor deploy` and with a README of its own: [Tasks](examples/python-fastapi), a FastAPI app run by uvicorn with a web page, SQLite in the app's data directory and migrations as the release command; [Links](examples/go-stdlib), a link shortener with only Go's standard library and a graceful stop; [Poll](examples/node-express), an Express API with a Vite front end built at deploy time; and [Handbook](examples/static-site), a static site with clean URLs, a 404 page, headers and redirects. CI deploys each one on Linux and macOS and checks its pages and its API.
- **A reference for `moorage.toml`.** [docs/manifest.md](docs/manifest.md) describes every setting as this release implements it, the variables Moorage sets, how apps are detected, and which settings are accepted but have no effect yet.
- **The logo.** Moorage's logo and icon, as SVG files in [docs/assets](docs/assets), in the README; the pages the server shows itself (for an unknown app, an app not deployed yet, an unavailable one) carry the icon and use it as their favicon.

### Changed

- **The server's admin token is local once the server has accounts.** It keeps working on the server's own machine, so `sudo moor …` needs no sign-in, but from any other machine it stops working once the server has been claimed. A server that is not claimed behaves as in 0.1.0.
- **The API's lists come in pages.** `GET /apps`, `/deployments` and `/releases` answer with `{"items": […], "next_cursor": "…"}` instead of an array, and take `?limit` and `?cursor`. This is a change for API clients of 0.1.0.
- **The documentation's layout.** `docs/` is the documentation for people who run Moorage and deploy apps to it — the guide, formerly `docs/guide/`, with an index; the design documents, the roadmap and the decisions moved to [`spec/`](spec/README.md). The README says what Moorage is and what works today, with a quick start. A test checks that every link in the README, the changelog, `docs/`, `spec/` and `examples/` leads to a file and a heading that exist.

## 0.1.0 (2026-11-03)

Moorage 0.1.0 is the first release: one binary, `moor`, that runs a server on Linux or macOS and deploys apps to it from their source. The server works out how to build Go, Python (uv), Node.js (npm) and static apps, or runs the build you give it, downloads and verifies the toolchains they need, and serves each app on its own hostname, over TLS with certificates from its own CA or your own, or behind your TLS proxy. Apps keep running while the server restarts, new releases take over without dropping requests, and a rollback takes a second. Variables and encrypted secrets configure apps. Deploys by `git push`, accounts and containers come in 0.2.0; the web console in 0.3.0.

### Added

- **The `moor` binary and a server that starts (wave 1, slice 1).** `moor version` prints the version, commit and platform (`--json` too). `moor server init` writes `server.toml` from a preset: `local` (this computer only, `*.localhost` on 127.0.0.1:8080, plain HTTP) or `lan` (a server on your network: ports 80, 443 and 2222 with Moorage's own CA, or, with `--behind-proxy`, plain HTTP on 127.0.0.1:8080 behind a TLS-terminating proxy such as nginx). It goes to `--config`, `$MOORAGE_CONFIG` or a default location — system-wide when run as root or an elevated Administrator, per-user otherwise — and the file explains every setting. `moor server run` reads it strictly: an unknown key, a syntax error or an invalid value is reported with its line, and every problem at once. The server prepares its data directory (private directories for keys, certificates, runtime state and backups), takes a lock so that only one server uses it, opens the SQLite database in WAL mode and applies migrations — after taking a snapshot of a database that already had a schema, keeping the three newest — and answers `GET /.moorage/health` on every hostname. It refuses a database migrated by a newer `moor`, and shuts down gracefully on interrupt or SIGTERM. Git pushes over SSH come in wave 2.
- **Static sites, served on their own hostnames (wave 1, slice 2).** `moor deploy --static [DIR] --app NAME` uploads a directory and serves it at `<app>.<domain>`; the app is created by its first deploy. The rules come from the `[static]` table of `moorage.toml` in the current directory (`dir`, `spa`, `clean_urls`, `not_found`, `trailing_slash`, `listing`, `[[static.headers]]` and `[[static.redirects]]` with `:name` and `*` placeholders, redirects or rewrites, and `force`), as [the manifest documentation](docs/manifest.md) describes. Pages are served with strong ETags, ranges, pre-compressed `.br` and `.gz` variants, and immutable caching for files whose names carry a content hash. Every deploy is a new numbered release; `moor releases` lists them and `moor rollback [vN]` serves an earlier one again in a moment. The routing table is swapped atomically: in tests, thousands of requests during repeated deploys and rollbacks never failed. `moor apps` lists the apps. Unknown apps, apps not deployed yet and unknown hostnames get small platform pages; `/.moorage/health` answers on every hostname.
- **TLS.** `tls.mode = "internal"` issues certificates on demand for the console's and the apps' hostnames, from a root Moorage generates on first start (limited by name constraints to the base domain and the console's hostname, and downloadable at `/.moorage/ca.crt`) or from an intermediate CA issued by your corporate CA (`tls.ca_cert`, `tls.ca_key`). `tls.mode = "files"` serves certificate files, such as a corporate wildcard, chosen by server name and reloaded when they change. With either, plain HTTP is redirected to HTTPS. With `tls.mode = "off"` and `[proxy]`, Moorage runs behind a TLS-terminating proxy such as nginx and gives out `https://` URLs.
- **The API and a bootstrap admin token.** `/api/v1` lists apps, deploys static sites, lists releases and rolls back, with errors as `application/problem+json`. Until accounts arrive, it is guarded by an admin token the server writes to `keys/admin-token` in its data directory (stored only as a hash); the CLI on the server's own machine finds the server and its token by itself, and elsewhere takes `--server`, `--token` and `--ca-cert` (or `MOOR_SERVER`, `MOOR_TOKEN`, `MOOR_CA_CERT`).
- **Apps that run (wave 1, slice 3).** `moor deploy --artifact [DIR]` uploads an app that is ready to run — a compiled binary, or a script for an interpreter on the host — and runs the processes declared under `[processes]` in `moorage.toml` (with `[deploy]` and `[env]`). Each instance gets a port of its own on 127.0.0.1 (`$PORT`), Moorage's variables (`MOORAGE_APP`, `MOORAGE_RELEASE`, `MOORAGE_URL`, `MOORAGE_DATA_DIR` and others), a persistent data directory and a temporary one. A new release takes over only once all its instances are healthy (an HTTP check of `health.path`, or a TCP check of the port); traffic then moves to exactly the new instances and the old ones finish their requests before they stop. If a new instance fails, the previous release keeps serving and the deploy reports the app's last output. `[deploy] strategy = "recreate"` stops the old instances first. Each instance runs under a small supervisor, `moor shim`, which writes its output to a rotated log, restarts it with growing delays when it exits (and slows down a crash loop), and keeps it running while the server restarts: a restarted server adopts running instances before it opens its listeners. When a shim dies, its app goes too — on every operating system — and the server starts a replacement. Instances that fail their health checks get no traffic and are restarted. Commands that are not simple (`cd web && ./server`) run in an embedded POSIX shell, the same on Linux, macOS and Windows. `moor ps` lists the instances, `moor logs [-f] [--process web]` shows their output merged by time, and `moor restart` replaces them without downtime; `moor rollback` works for apps as for static sites, and a static deploy to an app stops its processes.
- **The proxy.** Requests are spread over an app's healthy instances by the number of requests in flight, and a refused connection is retried once on another instance. Upgraded connections (such as WebSockets) and streamed responses pass through. Apps receive `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host`, `Forwarded`, `X-Real-IP` and `X-Request-Id`; headers a client sends for these are believed only from a trusted proxy (`[proxy] trusted`), and `X-Moorage-*` headers from clients are removed. Every request to an app is written to `logs/router/<app>/<env>.log`; the server's own log is also written to `logs/server/moorage.log`. Both are rotated.
- **Apps built from source (wave 1, slice 4).** `moor deploy [DIR]` uploads an app's source — leaving out what `.gitignore` and `.moorignore` exclude, and `node_modules`, `.venv` and `.git` — and the server builds it in the directory it will run from, then shows the build as it happens. Without a manifest, Moorage detects the app: Go (`go.mod`; the binary is built and run), Python (`pyproject.toml` or `requirements.txt`, installed with uv into a virtual environment; the web command is the project's script, or a FastAPI, Starlette, Django or Flask app found in the code), Node.js (`package.json`, installed with npm and built with the build script; the start script runs the app, and without one the build's `dist/` is served as a static site) or a static site; `runtime = "command"` and `"binary"` run any other build and app, and a `Procfile` is honoured. The `[release]` command runs once per deployment, before the new release takes traffic (a failure leaves the previous release serving), and `on_create` after an environment's first release. Every deployment is recorded with its status and log: `moor deployments` lists them, `moor deployments show` and `moor deployments follow` show one, and `--detach` or Ctrl-C leaves a deployment running. A newer deployment supersedes one still waiting. Old builds beyond `[deploy].keep_releases` are removed; `moor rollback` to one of them says so.
- **Toolchains, downloaded and verified.** Go, Node.js, uv and Python are installed on demand into the data directory, each download checked against the SHA-256 its project publishes (Python through uv, which carries the checksums). Versions may be partial (`go 1.26` in `go.mod`, `24` in `.nvmrc`, `3.13` in `.python-version`) or a range (`>=22` in `engines.node`): the newest matching release is used and recorded in the build. Builds share download caches. Mirrors for proxies and air-gapped networks go under `[toolchains]` in `server.toml`.
- **The whole manifest.** Every table of `moorage.toml` version 1 is read and checked, with every problem reported at once; settings this version does not act on yet are reported as warnings. `moor manifest validate` checks a manifest, `moor manifest explain` shows how Moorage will build and run an app, and `moor manifest schema` prints a JSON Schema for editors.
- **Variables and secrets (wave 1, slice 5).** `moor env set NAME=value…` configures an app without changing its code: the variables override `[env]` of `moorage.toml`, for one environment or, with `--all-envs`, for all of them, and `--build` makes them available to builds too. Every change is a new release of the current build, rolled out without downtime (`--no-restart` keeps it for the next deploy); every release records its variables, and `moor rollback --with-config` restores an earlier release's. `--secret` values are encrypted (AES-256-GCM, with a data key per app sealed by the master key in `keys/master.key`, which must be backed up apart from the database), never shown again, kept out of app, build and release-command logs, and handed to apps in memory, never through a file. `moor env` lists the variables and where each comes from; `moor env unset`, `moor env import FILE` (a `.env` file) and `moor env export` complete it. A secret's value can be read from standard input, or typed without echo, so that it stays out of the shell's history.
- **The server as a service.** `moor server install` installs and starts the server as a systemd unit on Linux or a launchd daemon on macOS (as root; or as a service of your own user), set up so that stopping or restarting it leaves the apps running for the server to take over again. `moor server status`, `start`, `stop` (`--all` stops the apps too), `restart` and `uninstall` drive it.
- **A guide.** [Installing Moorage](docs/install.md), quick starts for [Go](docs/go.md), [Python](docs/python.md), [Node.js](docs/node.md), [static sites](docs/static.md) and [anything else](docs/other.md), and [variables and secrets](docs/variables.md).
- Continuous integration: formatting, `go vet` and the tests on Linux, macOS and Windows (with the race detector on Linux), a build of all six targets (Linux, macOS and Windows on amd64 and arm64) with cgo disabled, and `govulncheck`; the sample apps are built from source on Linux and macOS, and the server is installed as a service, restarted with an app under load, and uninstalled, on Linux and macOS. Pushing a `v*` tag builds the binaries with their SHA-256 checksums and drafts a GitHub release from this changelog.
