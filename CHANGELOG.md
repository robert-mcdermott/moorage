# Changelog

## Unreleased

### Added

- **The `moor` binary and a server that starts (wave 1, slice 1).** `moor version` prints the version, commit and platform (`--json` too). `moor server init` writes `server.toml` from a preset: `local` (this computer only, `*.localhost` on 127.0.0.1:8080, plain HTTP) or `lan` (a server on your network: ports 80, 443 and 2222 with Moorage's own CA, or, with `--behind-proxy`, plain HTTP on 127.0.0.1:8080 behind a TLS-terminating proxy such as nginx). It goes to `--config`, `$MOORAGE_CONFIG` or a default location — system-wide when run as root or an elevated Administrator, per-user otherwise — and the file explains every setting. `moor server run` reads it strictly: an unknown key, a syntax error or an invalid value is reported with its line, and every problem at once. The server prepares its data directory (private directories for keys, certificates, runtime state and backups), takes a lock so that only one server uses it, opens the SQLite database in WAL mode and applies migrations — after taking a snapshot of a database that already had a schema, keeping the three newest — and answers `GET /.moorage/health` on every hostname. It refuses a database migrated by a newer `moor`, and shuts down gracefully on interrupt or SIGTERM. Git pushes over SSH come in wave 2.
- **Static sites, served on their own hostnames (wave 1, slice 2).** `moor deploy --static [DIR] --app NAME` uploads a directory and serves it at `<app>.<domain>`; the app is created by its first deploy. The rules come from the `[static]` table of `moorage.toml` in the current directory (`dir`, `spa`, `clean_urls`, `not_found`, `trailing_slash`, `listing`, `[[static.headers]]` and `[[static.redirects]]` with `:name` and `*` placeholders, redirects or rewrites, and `force`), as [the manifest documentation](docs/03-manifest.md) describes. Pages are served with strong ETags, ranges, pre-compressed `.br` and `.gz` variants, and immutable caching for files whose names carry a content hash. Every deploy is a new numbered release; `moor releases` lists them and `moor rollback [vN]` serves an earlier one again in a moment. The routing table is swapped atomically: in tests, thousands of requests during repeated deploys and rollbacks never failed. `moor apps` lists the apps. Unknown apps, apps not deployed yet and unknown hostnames get small platform pages; `/.moorage/health` answers on every hostname.
- **TLS.** `tls.mode = "internal"` issues certificates on demand for the console's and the apps' hostnames, from a root Moorage generates on first start (limited by name constraints to the base domain and the console's hostname, and downloadable at `/.moorage/ca.crt`) or from an intermediate CA issued by your corporate CA (`tls.ca_cert`, `tls.ca_key`). `tls.mode = "files"` serves certificate files, such as a corporate wildcard, chosen by server name and reloaded when they change. With either, plain HTTP is redirected to HTTPS. With `tls.mode = "off"` and `[proxy]`, Moorage runs behind a TLS-terminating proxy such as nginx and gives out `https://` URLs.
- **The API and a bootstrap admin token.** `/api/v1` lists apps, deploys static sites, lists releases and rolls back, with errors as `application/problem+json`. Until accounts arrive, it is guarded by an admin token the server writes to `keys/admin-token` in its data directory (stored only as a hash); the CLI on the server's own machine finds the server and its token by itself, and elsewhere takes `--server`, `--token` and `--ca-cert` (or `MOOR_SERVER`, `MOOR_TOKEN`, `MOOR_CA_CERT`).
- Continuous integration: formatting, `go vet` and the tests on Linux, macOS and Windows (with the race detector on Linux), a build of all six targets (Linux, macOS and Windows on amd64 and arm64) with cgo disabled, and `govulncheck`. Pushing a `v*` tag builds the binaries with their SHA-256 checksums and drafts a GitHub release from this changelog.
