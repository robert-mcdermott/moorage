0.10.1 (2026-11-06)#

Moorage 0.10.1 fixes two things about stopping a server, for those who have more than one server on a machine, or use services.

To upgrade from 0.10.0, run moor server upgrade. Running apps are taken over without a restart, and moor server upgrade --rollback goes back. This release does not change the database.

Fixed#

  • moor server stop --all and moor server uninstall left services running, so that uninstalling Moorage could leave a database running that nothing looked after. They now stop them, after the apps, and what they hold stays in their volumes. The server starts them again when it next starts. --keep-apps leaves them running, as it does apps.
  • moor server uninstall, start and restart went by the name of the service, and not by which server it runs. A server tried out with a configuration or a home directory of its own could take away the real one's service. They now leave it alone, as moor server stop already did. If yours was installed with a --config of its own, pass the same one, as they say if you do not.
  • With engine = "auto" and both Podman and Docker installed, stopping everything only looked in the first. A server takes whichever answers, so that what it ran could be in the other. It now looks in both.
  • moor server uninstall with no service said that it had removed one, and stopped the apps of a server that might be running without one. It now says that there is none, and leaves them. moor server stop --all stops them.

0.10.0 (2026-11-05)#

Moorage 0.10.0 runs a database for your app. Say [services.db] and type = "postgres" in moorage.toml, or type = "s3" for object storage, and each environment gets its own, with its address given to the app as it starts. They run in containers, so that they take Podman or Docker, and only those who use them need one.

What this is not. In production, a service is one container with no replica, kept by backups: a convenience, and not database hosting. For a database that matters, set DATABASE_URL on production to one that is looked after, and let previews use their own. Apps on a machine are kept apart from a service by its password, and not by the network. Real PostgreSQL and object storage are tried under both engines in CI on Linux, and nowhere else: on macOS and Windows, a service's data lives inside the engine's machine, and goes with it. Everything before this that was untried still is: this release has not had an outside penetration test, or met Let's Encrypt itself, Cloudflare, or a webhook directly from GitHub, and setting up Kiro comes from its documentation alone.

To upgrade from 0.9.0, run moor server upgrade. Running apps are taken over without a restart. This release changes the database, so that moor server upgrade --rollback puts the previous one back. Nothing about an app changes unless its manifest names a service, and a server that has none never asks for an engine because of them.

Added#

  • [services.<name>], with type = "postgres", versions 15 to 18, or type = "s3", which is Versity Gateway on plain files, with one bucket and one key under the names that clients look for. Each environment and each preview has its own, with a random password. A service is made before a release, so that a release command can migrate, and one that does not become ready fails the deployment with the previous release still serving. Nothing is ever called latest.
  • Previews are empty, unless you opt in. seed = "production" starts a new preview with production's latest dump, where nothing can connect until sanitize has run. That is refused for a preview anyone can reach, one from a fork, and one that a coding agent's token made. A later commit or moor access cannot open the gate over such a copy. A preview never ends up on production's database by inheritance.
  • Sleep. An environment's services stop with it and keep what they hold, and waking starts them first. A command or a cron job starts what it needs for as long as it runs.
  • Backups hold a dump of each service of production and of the named environments, made just before: pg_dumpall, or a tar of the object store. Volumes are not in a backup. After a restore to a new machine, a service loads its dump by itself before anything can connect to it. moor services restore goes back to the dump on the machine that it ran on, into a new volume, so that one that will not load changes nothing.
  • moor services, with logs, update, upgrade --to, restore and remove. moor logs --service db reads what one has said. A new major version is refused at deploy, and moor services upgrade moves its data with the newer version's tools and checks that it holds what it did. After an upgrade or a restore, the old volume stays until --finish lets go of it, or --back goes back to it.
  • A Services tab in the console, with what each has said and uses, and what an app's services add up to across its environments, as each preview has its own. What one uses is also in metrics, as service.db. moor server doctor says if one that should be running is not, and events say when one is made, restarted or removed.

Changed#

  • A cold rootless Podman is given 15 seconds to answer for the first time, rather than 3, as that failed a first deployment.
  • CI does not test the same code twice. A merge of a pull request that has passed takes about a minute, and the release of a commit that has passed reuses that.

0.9.0 (2026-11-05)#

Moorage 0.9.0 lets coding agents deploy to it and read how it went. moor mcp is a small server for Claude Code, Codex and others, which refuses a token that can do everything, and moor mcp setup makes a narrow one and connects a client. A token can be limited to previews, and moor agent init tells an agent how to use all of this.

What that limit does not do. A token limited to previews reaches only the previews it makes, and is refused everything else, including what is added to Moorage later. Those previews take nothing of production's variables or those set for every environment. The code it deploys still runs on your server, and on Linux an app's environments share a user, so that a preview's code can read production's data. To keep what an agent makes from production altogether, give it an app of its own. Coding agents says so at more length, and is worth reading first.

This release also fixes a bug that matters if you run containers: apps with runtime = "image" or "dockerfile" lost [environments], [[cron]], [vars] and strip_prefix, silently. And it makes Podman and Docker provably optional, ahead of the services planned for 0.10.0, which only those who use them will need an engine for.

To upgrade from 0.8.0, run moor server upgrade. Running apps are taken over without a restart. This release changes the database, so that moor server upgrade --rollback puts the previous one back. Some things to know:

  • A container app's [environments], [[cron]], [vars] and strip_prefix now count. If yours has a [[cron]] that never ran, or a required variable that was never asked for, they will now.
  • Deploying an image to a server whose engine cannot run it is refused at once, with a 409, rather than failing as a deployment.
  • source=build in an environment's logs now shows that environment's builds and runs, and not those of all of an app's environments.
  • keep_releases is now production's to say. What a branch's manifest says no longer decides how many releases of the others are kept, which a preview could have used to remove production's way back.
  • With the engine not answering, restarting, scaling, rolling back, changing variables, putting to sleep or deleting a container app now says why it cannot, with a 409, and changes nothing, rather than appearing to or answering 500. So does deploying a static site over one.

Added#

  • moor mcp, a small Model Context Protocol server for coding agents, on standard input and output. It reads apps, deployments, releases and logs, and checks a local manifest. With --allow-deploy, it can deploy, roll back and restart. Nothing in it runs commands, reads secrets or deletes anything, and it reads local files only below where it started or --root, which cannot be your home directory or above it. What an app wrote is marked as untrusted, with what draws nothing removed. It refuses a token that can do everything, and does not fall back on what moor login stored. See Coding agents.
  • moor mcp setup makes a narrow, expiring token, keeps it in a context of its own, and tells a client of the server: Claude Code, Codex, VS Code, Gemini CLI, Cursor, Kiro's IDE and CLI, and others. Running it again makes the new token before it revokes the one that context held, and leaves another machine's alone, and it will not replace a context that moor login made.
  • moor agent init adds a section of AGENTS.md and an Agent Skill to a repository, which teach an agent to use Moorage, and what to be careful of. It keeps your line endings, leaves alone a file whose markers it does not understand, and writes nothing through a link.
  • A token can be limited to previews, with moor tokens create --envs previews or in the console. It deploys only to a name starting with agent-, which makes a preview that takes nothing of production's, and is refused everything else, deny by default. It limits what a token can ask for, and not what the code it deploys can do: Coding agents says where that stops.

Changed#

  • A container engine is provably optional. An app that does not run in a container never causes the server to ask for one, and a test holds it to that. The server finds out as it starts without waiting, and again only when something wants to know, so that starting Docker Desktop later or installing Podman needs no restart. GET /api/v1/server says how it stands, an image is refused at once if it cannot run, and anything else that needs one fails before it builds, with what to do. See The engine.
  • auto prefers an engine that answers to the first one found. Once an image has been built or fetched under one, it stays with that one while anything here needs it, as the image is in its store, and until then an engine that only answered holds nothing.

Fixed#

  • A container engine that was down at start lost track of its containers. Their records were marked as stopped, and new ones were started every ten seconds. Now nothing changes until it answers, when the same containers carry on, and server.engine_down says what is happening.
  • What an engine did could hold up a server. Commands that stop or remove a container now have a time limit, so that a daemon that hangs cannot hold an environment for ever, and a server with apps in containers waits a few seconds for it as it starts, and takes over the rest once it answers. Looking at how the server stands answers at once.
  • A container that could not be stopped was recorded as stopped. It now stays on the record until the engine answers, and is no longer served.
  • A daemon that was down could be taken for a container that had gone, because of how an engine with no socket words its error. The app was marked as lost, and another was started beside it once the daemon returned.
  • gRPC apps in containers lost h2c when a server restarted.
  • Build logs were shown under every environment of an app, so that reading a preview's could show production's.
  • A branch's manifest could decide how many releases the others kept. It is now production's manifest that says.
  • Container apps lost part of their manifest. With runtime = "image" or "dockerfile", [environments], [[cron]], [vars] and strip_prefix were silently ignored: no named environment, no cron job, and no required or generated variable. They now count, and an environment's resources reach the engine.

0.8.0 (2026-11-04)#

Moorage 0.8.0 can take itself beyond the firewall: it gets certificates from a public CA by itself, and has a preset for a server on the internet, with what two close reviews of it found fixed. It speaks gRPC and keeps sessions sticky. Its connections to GitHub, GitLab, Gitea, OpenTelemetry and syslog have now met the real thing.

It has not had an outside penetration test, which this release was meant to include: that takes someone engaged to do it. Until then, Security says what we would do, which is to keep a server on a network you control, or behind something that decides who reaches it.

What has been tried: GitHub by hand, with a real repository, and GitLab, Gitea, an OpenTelemetry collector, syslog-ng, a gRPC client and Pebble in CI, on each change to that code. What has not: a certificate from Let's Encrypt itself, a record set at Cloudflare, a webhook delivered directly by GitHub, and a real fork on GitHub.

To upgrade from 0.7.0, run moor server upgrade. Running apps are taken over without a restart, and moor server upgrade --rollback goes back. Some things to know:

  • A static site no longer serves what starts with a dot, except .well-known. If yours means to, say dotfiles = true under [static].
  • Viewers see less. A release's manifest, which variables changed, and with --viewers-see-logs=false what a failed deployment printed and the commands people ran, are kept from them.
  • A token limited to one app can no longer read projects, and a token that can only read cannot mark notifications as read. A script that did either needs a different token.
  • Reading an app that is not there answers 404 throughout. A few routes gave an empty list or a 409.
  • A deleted app's events go with it. The audit log keeps what happened.
  • A failed build or release command no longer quotes itself in its message. A script that looked for the command there should look in the log.

Added#

  • Certificates from a CA. tls.mode = "acme" gets certificates from Let's Encrypt, any other CA, or an internal ACME server: for each hostname the first time it is wanted, by HTTP-01 or TLS-ALPN-01, or one for the whole domain by DNS-01, through Cloudflare, RFC 2136 or a program of your own. Only what the server serves gets one, so that nobody can use up a CA's limits by making up names. They are renewed by themselves, and a certificate that cannot be had reaches those concerned. See TLS and trusting the server.
  • The public preset, moor server init --preset public, for a server on the internet: certificates from a CA, and everything but production behind a sign-in.
  • hsts under [tls] tells browsers to use nothing but HTTPS for each hostname, and the public preset turns it on. See Staying on HTTPS.
  • gRPC. protocol = "h2c" on a web process runs a server that speaks only cleartext HTTP/2. Streams work both ways, trailers come through, and clients can reach it with TLS or, on the plain listener, without. See gRPC.
  • Sticky sessions. sticky = true on a web process keeps a browser with the instance it first reached, by a cookie that the app does not hear. See Scaling.
  • A website, at https://robert-mcdermott.github.io/moorage/: what Moorage is, and all of its documentation, in both themes, with a search. node docs/site/build.mjs makes it from the guides in docs, so that the two say the same, and fails on a broken link, which CI now checks. See the website's README.
  • Screenshots in the guides, all taken from a real server by node docs/capture/capture.mjs, which starts one, deploys the examples, and makes some requests.
  • New guides: Getting started, Concepts, Releases, rollbacks and scaling, Logs, Server configuration, Running a server, Architecture and Security.
  • A reference of every command, made from the commands themselves, and an API reference on the website, made from the OpenAPI document. A test keeps the first the same as the commands.

Changed#

  • Viewers see what the table of roles says, and no more. A release's manifest and which variables changed, in the API, the console and the activity feed, are for those who can deploy. --viewers-see-logs=false now also keeps back what a failed deployment printed and the commands that people ran.
  • A token limited to one app is limited to it. It is refused projects and their members, as it should have been. A token that can only read can no longer mark notifications as read.
  • What a project hides looks like what is not there. The API, the console and git give the same answer for an app or a project someone has no role in as for one that does not exist, and reading a missing app now always answers 404, where a few routes gave an empty list or a 409. Accounts says where that stops.
  • What the server does on its own account is for administrators: backups, certificates, disk space and starting up are no longer in everyone's activity.
  • Deleting an app deletes its events, so that whoever takes its name, perhaps in another project, does not inherit them. The audit log keeps what happened.
  • A failed build or release command says how it ended and not what it was, as more people read that than can read the command. The log still says.
  • A static site no longer serves files and directories whose names start with a dot, such as a .env or .git left in the directory, except .well-known. dotfiles = true under [static] serves them as before.
  • Tried against the real thing. .github/scripts/real-services-check.py drives GitLab, Gitea, an OpenTelemetry collector, syslog-ng, a gRPC client and Pebble in CI, and GitHub was tried by hand. They found that GitLab wants a Maintainer's token and asks for a fork's commit by its merge request's ref, and that moor run lost the quoting of the words it was given.
  • moor forge connect checks a token with the forge, and refuses one that it does not accept, or that cannot see the repository, and says so, leaving what was there as it was. Before, a bad token was taken, and found out from the first pull request. A forge that cannot answer at that moment is no reason to refuse.

Fixed#

  • The list of apps could name those you cannot see. Its cursor came from the next app, whoever's it was, so that going through the list one at a time read off every name on the server. Pages now end at what you can see, and do not come up short.
  • An open log could outlast a role. Following a deployment's log now ends within a minute of losing the right to read it, as other streams do.
  • The address guard took some IPv6 addresses at face value. ::7f00:1, 64:ff9b::7f00:1 and 2002:7f00:1:: all stand for 127.0.0.1 on some networks, and are now judged as that.
  • Going away could wait for something that a container engine's command had left running, for as long as that ran. It now waits two seconds, as other commands do.
  • An open redirect on static sites. A path with a backslash in it, such as /%5Cevil.example//, was redirected to /\evil.example/, which browsers read as another site. A link on your domain could send someone anywhere. Such a path is now not found, as is one with a control character.
  • A way to pass an identity to some apps. A client could send X.Moorage.User, which an app served through CGI or the like reads as X-Moorage-User, the header Moorage uses to say who signed in. Every spelling of the platform's headers is now removed: underscores already were, and dots and the rest now are.
  • Renaming an app on Windows waits longer for a virus scanner to finish with its builds: six seconds was sometimes too few.
  • moor run and moor exec keep your words as you gave them. moor run -- sh -c "echo a; echo b" ran as sh -c echo a; echo b, and an argument with a space in it, like moor run -- python -c "print('hi')", came apart. Several words are now quoted, and one word is still a command line for the server's shell: moor run -- 'echo a && echo b'.
  • Going back from an upgrade on macOS could leave the server stopped, when it took longer to stop than launchd took to be told to start it, which it then ignores. moor server stop now waits for it too, so that moor server start straight afterwards works.
  • moor server status no longer reports a service on this machine that runs another server as if it were this one's.
  • The console's tables no longer break a name, an address or an email in the middle of a word when a window is narrow: the list of apps at a laptop's width, say.

0.7.0 (2026-11-04)#

Moorage 0.7.0 brings the server to Windows, connects it to where your code is kept, and lets you into what it runs. A push or a pull request on GitHub, GitLab or Gitea can deploy by itself, with a preview for each pull request. moor run -it is a terminal in an app, and the console can run commands and show its data directory. Logs and metrics can go to where your team already looks, and thresholds say when to be told.

To upgrade from 0.6.0, run moor server upgrade. Running apps are taken over without a restart, and moor server upgrade --rollback goes back. Nothing you have set up behaves differently. Some things to know:

  • On Windows, apps run as the server's own account, as there is nothing there yet to keep them apart. They can read its database and master key, so anyone who can deploy to a server on Windows can reach every secret on it, whichever project they are in. See How apps are kept apart.
  • moor server install on Windows closes the data directory to everyone but the service, so it refuses the top of a drive, or anyone's profile. A data directory has to be a folder of its own.

Connecting to a real forge, OpenTelemetry collector or syslog server has been tried against stand-ins that follow their published formats, and not against the real thing. If yours disagrees, please say so.

Added#

  • A server on Windows, as a service. moor server install, in an elevated terminal, makes a Windows service that runs as an account of its own with few rights, and apps run as it too. [resources] is enforced there by Job Objects, which an app is inside from before it runs. moor server resolver install adds a block to the hosts file. See installing.

  • Deploying from a forge. moor forge connect, or the Repository section of an app's settings, connects an app to a repository on GitHub, GitLab or Gitea, or anything else that can sign a webhook. A push to the default branch deploys to production. Each pull request gets a preview, with a check on its commit and one comment that says where it is, and it goes when the pull request closes. What is deployed is what is fetched from the repository, whatever an event says, and a pull request's manifest cannot send it anywhere but its own preview. A pull request from a fork or from someone the forge does not vouch for is not fetched or built until a maintainer approves that commit, and another commit waits again. A server that a forge cannot reach can look every minute instead, with --poll. See Deploying from a forge.

  • A terminal. moor run -it -- /bin/sh gives you a terminal in a one-off instance of the current release, on Linux, macOS and Windows, as the app's user and within its limits. moor exec INSTANCE -it does it in a running container. Losing the connection stops what was running, a token that may no longer do this ends it, and what is said in one is not kept. See Getting into an app.

  • A console in the browser. An app's Console tab runs one command at a time, and shows what it says as it says it.

  • The data directory. An app's Files tab and moor files list, download, upload and remove what is in an environment's data directory. What an app has left there cannot lead the server out of it: a link out is not followed, nor is a pipe opened, and a file is only ever sent as a download.

  • Telemetry elsewhere. moor server telemetry, or Settings then Telemetry, sends what apps say to syslog (RFC 5424, over UDP, TCP or TLS), an OpenTelemetry collector or any HTTP endpoint, and what they do to an OpenTelemetry collector. A sink that is down costs nothing but its own place in a queue, and what apps say while the server restarts is sent when it is back. See Sending telemetry elsewhere.

  • Thresholds. moor alerts, or an app's Metrics tab, says when to be told about an environment's error rate, latency, memory or CPU, through the channels that notifications already go to. [notifications] disk_percent says how full the server's data volume may get.

Fixed#

  • A backup could fail, rarely, if an app swapped a file between a link and a plain file as it was being read, and back again. It now notes that the file changed, as it does for one that is changing.

0.6.0 (2026-11-04)#

Moorage 0.6.0 is about a server you can rely on. On Linux, apps are kept apart from one another. Backups and restoring are built in, and were tried on real services. People can sign in with a second factor, through your identity provider, or through a proxy. A server can upgrade itself, and go back. Moorage is now open source, under the Apache License 2.0.

To upgrade from 0.5.0, run the installer once and restart the server, as moor server upgrade starts with this version. Running apps are taken over without a restart. Some things behave differently:

  • On a server that runs as root on Linux, apps get users of their own as they next start. That is the system service, as level = "auto" under [isolation] means this. An app can then only write to $MOORAGE_DATA_DIR and $TMPDIR, as its build is read-only, and cannot read what only root can. level = "none" keeps it as it was while you look into anything that minds. Instances that go on through the upgrade go on as root until they restart: Settings → System and the app's page say which, and moor restart APP does it with no downtime. See isolation.
  • To go back to 0.5.0, stop the server, put the copy of the database that this version kept in backups in the data directory in the place of moorage.db, and give the installer MOOR_VERSION=v0.5.0. 0.5.0 refuses a database that has moved on.
  • A site's directory has to be inside its build. One reached through a link to somewhere else now fails the build.

Added#

  • Apps kept apart on Linux. A server running as root gives each app an operating system user of its own, and its builds another: its data is its own, its build is read-only, and other apps cannot read its secrets. level = "sandbox" under [isolation] in server.toml adds Landlock and no_new_privs. See how apps are kept apart.
  • [resources] outside containers. Memory, CPU and process limits for any app, enforced by the kernel where the server runs as root on Linux. Elsewhere an instance that stays over its memory limit is restarted, and the console says what is not held to. An instance killed for its memory says that it ran out of memory.
  • Backups. moor server backup and Settings → Backups make a backup of a running server, on demand or on a schedule, to a directory or a bucket on S3 or a service like it. moor server restore brings it all back: apps, data, secrets and accounts. A restore checks everything before it changes anything, and is tried in CI. See backups.
  • Two-factor sign-in. Your account → Two-factor adds a code from an authenticator app to signing in, with recovery codes for if you lose it. See accounts.
  • Single sign-on. Settings → Sign-in connects to any OpenID Connect provider, with accounts made the first time, roles from groups, and an option to turn off passwords. trusted_header under [auth] believes a proxy that signs people in. See how people sign in.
  • moor server upgrade. A server upgrades itself: it checks a release against its published checksum, keeps a copy of the database and the binary, swaps them, restarts, and goes back by itself if the new version does not come up. --rollback goes back later on. Apps keep running throughout. Releases now come with a list of what went into them, and an attestation of the workflow that built them. See upgrading.
  • The server's configuration, as a file. moor server config export writes out people, projects, registries, notifications, backups and sign-in, with no secrets, and moor server config import brings it in on that server or another, with --dry-run to look first. See the server's configuration.
  • Node.js downloads are checked against its signature. The checksums of a Node.js release have to be signed by one of its releasers, whose keys come with moor. A new releaser's key needs a new moor, or signatures = "warn" under [toolchains]. A signature that is wrong is always refused.

Fixed#

  • A deployment could bring the release before it back. What keeps instances running could look at the current release just before a deployment recorded the new one, and start an instance of the old one after the rollout had finished. That instance then took the traffic, until the next deployment. It was rare, and has been possible since 0.1.0. A release is now recorded before its instances take the traffic, and an instance of any other release is stopped.

0.5.0 (2026-11-04)#

Moorage 0.5.0 is about apps once they are running. They can have cron jobs and one-off commands, charts of how they are doing, and notifications when they are not. Drop a folder in the console and it is a static site, with every release at an address of its own. A server of 4 CPUs and 8 GB holds 60 environments with sleep on, as measured. Moorage is now licensed under the Apache License 2.0.

Upgrading from 0.4.0 needs no steps of its own: replace moor and restart the server, and running apps are taken over without a restart. Some things behave differently:

  • [[cron]] in a manifest now runs. It was accepted and did nothing, and moor manifest validate warned of that. Its jobs start with the next deployment.
  • [vars.NAME] now counts. A deployment fails early if a required one is missing, and one to generate is made.
  • watch in [app] now counts. A push that touches none of those paths is kept, and not deployed.

Fixed#

  • Following an app's logs or a run's output now ends when you may no longer see them, within a minute.

Moorage 0.3.0 has a web console. Everything you run with moor you can now see and do at the server's console address: deploy, scale, restart and roll back apps; watch a deployment's stages and log as they happen; follow and search logs; change variables; manage your keys and tokens, and, as an administrator, users and registries. Every instance's output, live, merged by time: by process or instance, time range, text and source, with an app's builds, requests and events a click away, and only its problems at another. Pause, wrap, older lines and download. moor logs and the API have the same: --source, --grep, --since, --until, --instance and --problems.

New app says how to deploy one; a source archive or an image can be deployed from the page. See the console.

How many instances of each process run: new ones start beside those running, those beyond the number finish their requests and stop, and an instance that cannot start leaves the app as it was. 0.2.0 (2026-11-03)#

Moorage 0.2.0 is for teams. git push deploys an app, over SSH or HTTPS, with no git or sshd needed on the server, and shows the build in your terminal. Accounts, sign-in from any machine and scoped API tokens say who did what. Apps with a Containerfile, or an image from a registry, run in containers under Podman or Docker, released and rolled back like any other app. moor trust makes browsers accept the certificates of a server's own CA, moor server doctor checks a server and says how to fix what it finds, and moor server proxy-config nginx writes the configuration for running behind nginx. The documentation has moved up to docs/, with complete examples. The web console comes in 0.3.0.

Upgrading from 0.1.0 needs no steps of its own: replace moor and restart the server, and running apps are taken over without a restart (see Upgrading). Upgrade moor on other machines too: the API's lists now come in pages, which an older moor cannot read.

Added#

  • Deploys by git push (wave 2, slice 2). Every app has a git repository on the server, served over SSH (port 2222, listen.ssh) and HTTPS (/git/<app>.git on the console's hostname) by Moorage itself: no git or sshd is needed on the server. moor keys add registers an SSH key (Ed25519, ECDSA, or RSA of 3072 bits or more); moor git remote adds the app's remote to a repository, and git push moorage main deploys, with the build streamed back as remote: lines. The production branch is the repository's default branch (main, or the first branch pushed); other branches and tags are kept, not deployed. A failed deploy fails the push and leaves the branch where it was; Ctrl-C leaves the deploy running. The first push creates the app. [skip deploy] in a commit's message, or git push -o skip-deploy, keeps a commit without deploying it; -o detach accepts the push at once; -o env=production deploys any branch. Over HTTPS, moor git remote --http sets up moor git credential, which gives git the API token for the server's own git URL only. Repositories can be cloned back. moor deployments shows the branch and commit each push deployed, and other commands find the app from the moorage remote. See Deploying with git push.
  • Accounts (wave 2, slice 3). Users with email and password (Argon2id, at least 12 characters, common passwords refused) and a role: admins manage users, and until projects arrive members may do everything with apps. moor server init prints a one-time setup link to create the first account, so that nobody can race to claim a new server. moor login URL signs in from any machine by approving it in a browser (or --with-token), saving a context; moor logout, moor whoami and moor context go with it. moor server users creates users, who choose a password with a one-time link, and changes roles, disables and enables them. moor tokens makes API tokens with a scope (read, deploy, admin), an optional app and an expiry, stored only as hashes. SSH keys belong to their user. Git follows suit: pushes are recorded as their user's, tokens need the right scope, and a disabled user's keys and tokens stop working. Failed sign-ins and SSH handshakes slow down per address and account, and are logged as security events. Minimal pages on the console's hostname serve the claim, signing in, choosing a password and approving a sign-in; the session cookie is host-only, and forms and cookie-authenticated API requests need a CSRF token. See Accounts and access.
  • Containers (wave 2, slice 4). An app with a Containerfile or Dockerfile, or runtime = "dockerfile", is built into an image by Podman or Docker; runtime = "image", or moor deploy --image REF, runs one that is built already, pinned to its digest, so that restarts and rollbacks run exactly that image. Each runs like any other app: zero-downtime releases, health checks, rollbacks, logs, release commands, workers, variables and secrets. Containers publish only on the loopback interface, run with no-new-privileges and an init process, and get the environment's data directory at /data ([storage].mount). [container] sets the port, the user and the build, and [resources] memory, CPU and process limits. Moorage owns restarts: a container that exits is restarted by the process's restart policy, more slowly when it keeps exiting, and a kill for running out of memory is reported where the engine says so. Containers outlive the server, which finds them again by their labels, with no output lost or recorded twice; a server manages only its own. moor registry login keeps a private registry's credentials encrypted on the server. [containers].engine in server.toml chooses the engine: Podman if it is installed, or else Docker. CI runs all of it on both. See Running apps in containers and the new Guestbook example.
  • TLS and operations (wave 2, slice 5). moor trust puts a server's CA into the system's list and, on Linux, the browsers' own, and --remove takes it back. From the server's own machine it asks nothing; from elsewhere nothing vouches for the answer, so it shows the CA's fingerprint and what it may sign for, and asks, or takes --fingerprint. It refuses a server whose certificate does not come from the CA it offers. moor server status and the server's log show the fingerprint. moor server proxy-config nginx writes a configuration for nginx, which CI runs for real, deploying and pushing through it. moor server doctor checks a server, running or not, and says how to fix what it finds: its listeners, DNS, certificates, the container engine, the data directory and its keys, disk space, the clock, kernel features, and apps that can be reached without the router. --public-url checks the whole path through a proxy: forwarded headers, an app's hostname, WebSockets, streaming and large uploads, and with --timeouts, long silences. moor server resolver install makes *.localhost resolve for everything on macOS, with a rule in /etc/resolver and a small DNS responder in the server (listen.dns) that answers on loopback only. See TLS and trusting the server, Behind a TLS proxy and When something is wrong.
  • The API's contract. Every route declares the permission it requires, and a test enumerates them. docs/openapi.json, an OpenAPI 3.1 document generated from the routes and types and checked against them, is served at /api/v1/openapi.json. Errors can say what is wrong field by field. See The API.
  • Examples (wave 2, slice 1). examples/ has four complete apps, each ready to deploy with moor deploy and with a README of its own: Tasks, a FastAPI app run by uvicorn with a web page, SQLite in the app's data directory and migrations as the release command; Links, a link shortener with only Go's standard library and a graceful stop; Poll, an Express API with a Vite front end built at deploy time; and Handbook, a static site with clean URLs, a 404 page, headers and redirects. CI deploys each one on Linux and macOS and checks its pages and its API.
  • A reference for moorage.toml. docs/manifest.md describes every setting as this release implements it, the variables Moorage sets, how apps are detected, and which settings are accepted but have no effect yet.
  • The logo. Moorage's logo and icon, as SVG files in docs/assets, in the README; the pages the server shows itself (for an unknown app, an app not deployed yet, an unavailable one) carry the icon and use it as their favicon.

0.1.0 (2026-11-03)#

Moorage 0.1.0 is the first release: one binary, moor, that runs a server on Linux or macOS and deploys apps to it from their source. The server works out how to build Go, Python (uv), Node.js (npm) and static apps, or runs the build you give it, downloads and verifies the toolchains they need, and serves each app on its own hostname, over TLS with certificates from its own CA or your own, or behind your TLS proxy. Apps keep running while the server restarts, new releases take over without dropping requests, and a rollback takes a second. Variables and encrypted secrets configure apps. Deploys by git push, accounts and containers come in 0.2.0; the web console in 0.3.0.

Added#

  • The moor binary and a server that starts (wave 1, slice 1). moor version prints the version, commit and platform (--json too). moor server init writes server.toml from a preset: local (this computer only, *.localhost on 127.0.0.1:8080, plain HTTP) or lan (a server on your network: ports 80, 443 and 2222 with Moorage's own CA, or, with --behind-proxy, plain HTTP on 127.0.0.1:8080 behind a TLS-terminating proxy such as nginx). It goes to --config, $MOORAGE_CONFIG or a default location — system-wide when run as root or an elevated Administrator, per-user otherwise — and the file explains every setting. moor server run reads it strictly: an unknown key, a syntax error or an invalid value is reported with its line, and every problem at once. The server prepares its data directory (private directories for keys, certificates, runtime state and backups), takes a lock so that only one server uses it, opens the SQLite database in WAL mode and applies migrations — after taking a snapshot of a database that already had a schema, keeping the three newest — and answers GET /.moorage/health on every hostname. It refuses a database migrated by a newer moor, and shuts down gracefully on interrupt or SIGTERM. Git pushes over SSH come in wave 2.
  • Static sites, served on their own hostnames (wave 1, slice 2). moor deploy --static [DIR] --app NAME uploads a directory and serves it at <app>.<domain>; the app is created by its first deploy. The rules come from the [static] table of moorage.toml in the current directory (dir, spa, clean_urls, not_found, trailing_slash, listing, [[static.headers]] and [[static.redirects]] with :name and * placeholders, redirects or rewrites, and force), as the manifest documentation describes. Pages are served with strong ETags, ranges, pre-compressed .br and .gz variants, and immutable caching for files whose names carry a content hash. Every deploy is a new numbered release; moor releases lists them and moor rollback [vN] serves an earlier one again in a moment. The routing table is swapped atomically: in tests, thousands of requests during repeated deploys and rollbacks never failed. moor apps lists the apps. Unknown apps, apps not deployed yet and unknown hostnames get small platform pages; /.moorage/health answers on every hostname.
  • TLS. tls.mode = "internal" issues certificates on demand for the console's and the apps' hostnames, from a root Moorage generates on first start (limited by name constraints to the base domain and the console's hostname, and downloadable at /.moorage/ca.crt) or from an intermediate CA issued by your corporate CA (tls.ca_cert, tls.ca_key). tls.mode = "files" serves certificate files, such as a corporate wildcard, chosen by server name and reloaded when they change. With either, plain HTTP is redirected to HTTPS. With tls.mode = "off" and [proxy], Moorage runs behind a TLS-terminating proxy such as nginx and gives out https:// URLs.
  • The API and a bootstrap admin token. /api/v1 lists apps, deploys static sites, lists releases and rolls back, with errors as application/problem+json. Until accounts arrive, it is guarded by an admin token the server writes to keys/admin-token in its data directory (stored only as a hash); the CLI on the server's own machine finds the server and its token by itself, and elsewhere takes --server, --token and --ca-cert (or MOOR_SERVER, MOOR_TOKEN, MOOR_CA_CERT).
  • Apps that run (wave 1, slice 3). moor deploy --artifact [DIR] uploads an app that is ready to run — a compiled binary, or a script for an interpreter on the host — and runs the processes declared under [processes] in moorage.toml (with [deploy] and [env]). Each instance gets a port of its own on 127.0.0.1 ($PORT), Moorage's variables (MOORAGE_APP, MOORAGE_RELEASE, MOORAGE_URL, MOORAGE_DATA_DIR and others), a persistent data directory and a temporary one. A new release takes over only once all its instances are healthy (an HTTP check of health.path, or a TCP check of the port); traffic then moves to exactly the new instances and the old ones finish their requests before they stop. If a new instance fails, the previous release keeps serving and the deploy reports the app's last output. [deploy] strategy = "recreate" stops the old instances first. Each instance runs under a small supervisor, moor shim, which writes its output to a rotated log, restarts it with growing delays when it exits (and slows down a crash loop), and keeps it running while the server restarts: a restarted server adopts running instances before it opens its listeners. When a shim dies, its app goes too — on every operating system — and the server starts a replacement. Instances that fail their health checks get no traffic and are restarted. Commands that are not simple (cd web && ./server) run in an embedded POSIX shell, the same on Linux, macOS and Windows. moor ps lists the instances, moor logs [-f] [--process web] shows their output merged by time, and moor restart replaces them without downtime; moor rollback works for apps as for static sites, and a static deploy to an app stops its processes.
  • The proxy. Requests are spread over an app's healthy instances by the number of requests in flight, and a refused connection is retried once on another instance. Upgraded connections (such as WebSockets) and streamed responses pass through. Apps receive X-Forwarded-For, X-Forwarded-Proto, X-Forwarded-Host, Forwarded, X-Real-IP and X-Request-Id; headers a client sends for these are believed only from a trusted proxy ([proxy] trusted), and X-Moorage-* headers from clients are removed. Every request to an app is written to logs/router/<app>/<env>.log; the server's own log is also written to logs/server/moorage.log. Both are rotated.
  • Apps built from source (wave 1, slice 4). moor deploy [DIR] uploads an app's source — leaving out what .gitignore and .moorignore exclude, and node_modules, .venv and .git — and the server builds it in the directory it will run from, then shows the build as it happens. Without a manifest, Moorage detects the app: Go (go.mod; the binary is built and run), Python (pyproject.toml or requirements.txt, installed with uv into a virtual environment; the web command is the project's script, or a FastAPI, Starlette, Django or Flask app found in the code), Node.js (package.json, installed with npm and built with the build script; the start script runs the app, and without one the build's dist/ is served as a static site) or a static site; runtime = "command" and "binary" run any other build and app, and a Procfile is honoured. The [release] command runs once per deployment, before the new release takes traffic (a failure leaves the previous release serving), and on_create after an environment's first release. Every deployment is recorded with its status and log: moor deployments lists them, moor deployments show and moor deployments follow show one, and --detach or Ctrl-C leaves a deployment running. A newer deployment supersedes one still waiting. Old builds beyond [deploy].keep_releases are removed; moor rollback to one of them says so.
  • Toolchains, downloaded and verified. Go, Node.js, uv and Python are installed on demand into the data directory, each download checked against the SHA-256 its project publishes (Python through uv, which carries the checksums). Versions may be partial (go 1.26 in go.mod, 24 in .nvmrc, 3.13 in .python-version) or a range (>=22 in engines.node): the newest matching release is used and recorded in the build. Builds share download caches. Mirrors for proxies and air-gapped networks go under [toolchains] in server.toml.
  • The whole manifest. Every table of moorage.toml version 1 is read and checked, with every problem reported at once; settings this version does not act on yet are reported as warnings. moor manifest validate checks a manifest, moor manifest explain shows how Moorage will build and run an app, and moor manifest schema prints a JSON Schema for editors.
  • Variables and secrets (wave 1, slice 5). moor env set NAME=value… configures an app without changing its code: the variables override [env] of moorage.toml, for one environment or, with --all-envs, for all of them, and --build makes them available to builds too. Every change is a new release of the current build, rolled out without downtime (--no-restart keeps it for the next deploy); every release records its variables, and moor rollback --with-config restores an earlier release's. --secret values are encrypted (AES-256-GCM, with a data key per app sealed by the master key in keys/master.key, which must be backed up apart from the database), never shown again, kept out of app, build and release-command logs, and handed to apps in memory, never through a file. moor env lists the variables and where each comes from; moor env unset, moor env import FILE (a .env file) and moor env export complete it. A secret's value can be read from standard input, or typed without echo, so that it stays out of the shell's history.
  • The server as a service. moor server install installs and starts the server as a systemd unit on Linux or a launchd daemon on macOS (as root; or as a service of your own user), set up so that stopping or restarting it leaves the apps running for the server to take over again. moor server status, start, stop (--all stops the apps too), restart and uninstall drive it.
  • A guide. Installing Moorage, quick starts for Go, Python, Node.js, static sites and anything else, and variables and secrets.
  • Continuous integration: formatting, go vet and the tests on Linux, macOS and Windows (with the race detector on Linux), a build of all six targets (Linux, macOS and Windows on amd64 and arm64) with cgo disabled, and govulncheck; the sample apps are built from source on Linux and macOS, and the server is installed as a service, restarted with an app under load, and uninstalled, on Linux and macOS. Pushing a v* tag builds the binaries with their SHA-256 checksums and drafts a GitHub release from this changelog.
